## 一、为什么不是一个超级 Prompt？

最容易写出来的版本是：

```python
prompt = "请生成讲解文档、思维导图、练习题、阅读材料、代码和视频脚本……"
```

它有三个问题：

1. **角色冲突**：出题需要「诊断易错点」，微课需要「控制镜头时长」，讲解需要「先框架后细节」——一个 Prompt 很难同时把三种标准都讲清楚。
2. **失败不可隔离**：一次输出里某一段坏了，整份结果都要重来。
3. **不可观测**：你不知道是哪一个环节慢、哪一个环节质量差。

所以系统拆成 8 个角色：

| 角色 | 职责 | 产出 |
|---|---|---|
| 教学规划智能体 `planner` | 判断水平、定切入点、定顺序 | 资源计划 |
| 讲解文档智能体 `document_agent` | 建立框架、类比、自检 | Markdown |
| 思维导图智能体 `mindmap_agent` | 压缩成 4-5 个一级分支 | 树 + Mermaid |
| 出题智能体 `exercise_agent` | 针对易错点出题 | 选择题 + 简答题 |
| 拓展阅读智能体 `reading_agent` | 规划阅读路线 | 阅读清单 |
| 代码实操智能体 `code_agent` | 最小可运行示例 | 代码 + 任务 |
| 微课视频智能体 `video_agent` | 分镜、旁白、时长 | 分镜 + HTML 动画 |
| 质量审核智能体 `reviewer` | 规则打分 | 质量分 + 审核意见 |

> **多智能体的本质不是「Agent 越多越高级」，而是把不同的判断标准拆开，让每个角色只对一个目标负责。**

## 二、共享黑板：画像

所有 Agent 都从同一个 `AgentContext` 读取信息：

```python
@dataclass
class AgentContext:
    student: dict
    profile: dict[str, str]
    topic: str
    requirements: str
    task_id: str
    plan: dict
```

这对应架构设计里的 **Blackboard（黑板）模式**：

- 画像抽取 Agent 把结果写进 `profile_dimension`；
- 生成 Agent 从画像读「知识基础、认知风格、易错点」；
- 评估 Agent 再把新的掌握度写回画像。

好处是：**没有哪个 Agent 私自存一份画像**，所以「随学随新」只需要更新黑板，不需要通知每个 Agent。

## 三、编排：串行 → 并行 → 收口

`ResourceOrchestrator.generate()` 的流程：

```text
读取学生 + 画像
      │
      ▼
Planner（串行，因为它是后续并行的输入）
      │
      ▼
6 个生成 Agent（并行，互不依赖）
      │
      ▼
Reviewer（收口，统一打分）
      │
      ▼
按计划顺序落库 + 写 agent_run
```

核心代码：

```python
with ThreadPoolExecutor(max_workers=min(6, len(kinds))) as pool:
    futures = {
        pool.submit(self._run_one, ctx, kind, plan_map.get(kind, {})): kind
        for kind in kinds
    }
    for future in as_completed(futures):
        try:
            outputs.append(future.result())
        except Exception as exc:
            _trace(..., status="failed", error=str(exc))
```

这里用线程池而不是协程，原因很简单：当前业务是同步调用 LLM / 同步访问 MySQL，线程池已经足够；如果以后全部换成异步 SDK，再改 `asyncio.gather`。

**注意**：`ctx` 被多个线程共享，所以 Agent 只能读它，不能写它；每个 Agent 的产物通过返回值收集，最后由编排器统一落库。共享可变状态是最容易埋并发 bug 的地方。

## 四、结构化输出：让程序能消费

自然语言输出无法直接落库、渲染、判分。我们要求每个 Agent 返回固定 JSON Schema，例如出题：

```python
schema = {
    "type": "object",
    "properties": {
        "questions": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "id": {"type": "integer"},
                    "type": {"type": "string", "enum": ["single", "short"]},
                    "question": {"type": "string"},
                    "options": {...},
                    "answer": {"type": "string"},
                    "explanation": {"type": "string"},
                },
                "required": ["id", "type", "question", "options", "answer", "explanation"],
                "additionalProperties": False,
            },
        }
    },
    "required": ["questions"],
    "additionalProperties": False,
}
```

`BaseAgent.run()` 做了三件事：

1. 调 `llm_service.complete_json()`；
2. 校验顶层必填字段；
3. 把 dict 转成统一的 `AgentOutput`。

```python
def validate(self, data: dict) -> None:
    missing = [key for key in self.schema.get("required", []) if key not in data]
    if missing:
        raise ValueError(f"Agent 输出缺少字段：{missing}")
```

真实模型调用时，我们优先用 `output_config.format` 约束 JSON Schema；当前 SDK 版本没有暴露这个参数，所以通过 `extra_body` 透传。服务端不支持时，退回「提示词要求 JSON + 客户端提取 + 校验」。

> **工程原则：结构化输出不是「让模型乖一点」，而是让下游代码有确定的契约。**

## 五、失败处理：单个 Agent 失败不能拖垮整单

每次生成都可能遇到：超时、限流、返回缺字段、JSON 解析失败。编排器对每个 Agent 单独 `try/except`：

```python
except Exception as exc:
    logger.exception("资源智能体 %s 失败", kind)
    _trace(..., status="failed", error=str(exc)[:300])
```

只要还有一个 Agent 成功，接口就返回 200；全部失败才抛 `RuntimeError`。同时 LLM 层还有：

- SDK 自动重试（`max_retries=2`）；
- 业务层最多 3 次尝试；
- 最终降级 Mock，并标记 `mock-fallback`。

**降级不等于静默失败**：资源 `meta.provider`、`agent_run.status`、日志都会留下痕迹，前端也能看到。

## 六、可观测性：每个 Agent 一行记录

`agent_run` 表：

| 字段 | 作用 |
|---|---|
| `task_id` | 一次任务串联所有 Agent |
| `agent` / `role` | 谁在干活 |
| `status` | success / failed / fallback |
| `model` | template-engine / claude-opus-4-8 |
| `duration_ms` | 性能瓶颈 |
| `input_summary` / `output_summary` | 快速复盘 |
| `error` | 失败原因 |

前端「智能体运行轨迹」直接读这张表。答辩时可以指着时间线说清楚：**规划用了多久、六个生成器谁最慢、审核给了多少分**。

## 七、实际验证

一次 6 类资源生成的记录：

- 任务：`res-...`；
- 资源：document / mindmap / exercise / reading / code / video；
- 平均质量分：84.7；

- 视频 Agent 额外生成 `uploads/generated/{task_id}-video.html`，前端用 iframe 播放。

这些结果说明：**编排、并行、落库、追踪、前端渲染**已经连成一条完整链路。

## 八、踩坑与提醒

1. **不要伪造进度**。前端在等待时只显示「6 个 Agent 并行工作」，不假装某个 Agent 已经完成。
2. **Mock 与真实模型必须走同一套 Schema**。否则一开真实模型，前端就崩。
3. **Agent 之间不要直接互相调用**。横向调用会让依赖图变成蜘蛛网；统一由编排器调度。
4. **共享上下文只读**。需要写回的内容用返回值，由编排器落库。
5. **质量审核能用规则就别用大模型**。长度、主题覆盖、是否含结构化字段，这些规则稳定又便宜。
