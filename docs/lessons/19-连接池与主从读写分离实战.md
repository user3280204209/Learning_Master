## 一、为什么需要连接池？

最直观的写法是每次请求都：

```python
conn = pymysql.connect(**config)
...
conn.close()
```

问题不在「能不能连」，而在**建立连接很贵**：TCP 握手、身份认证、字符集协商、会话初始化。FastAPI 用线程池并发处理请求，每个请求都新建连接，延迟和资源消耗都会被放大。

连接池把「创建连接」从每次请求挪到第一次请求：

```text
请求 → 从池里取一个 → 用 → 还回池
         ↑ 取不到才创建
```

`db.py` 里的 `ConnectionPool` 做了四件事：

1. **LIFO 复用**：`queue.LifoQueue`，热连接优先被复用；
2. **池满等待**：最多等 5 秒，避免请求无限堆积；
3. **失效重建**：`conn.ping(reconnect=True)`，断线自动重连；
4. **释放前 rollback**：防止上一个请求的半截事务泄漏给下一个请求。

```python
def acquire(self):
    try:
        conn = self._pool.get_nowait()
    except queue.Empty:
        with self._lock:
            if self._created < self.max_size:
                self._created += 1
                return self._new_connection()
        conn = self._pool.get(timeout=5)
    conn.ping(reconnect=True)
    return conn
```

> 生产环境直接用 SQLAlchemy / DBUtils。手写一遍的意义是：你知道框架帮你做了什么，出问题时知道该看哪里。

## 二、读 / 写怎么选？

两种路线：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 显式 | 读接口 `read_conn()`，写接口 `write_conn()` | 简单、可控、事务清晰 | 每个接口要选对 |
| B 自动 | 解析 SQL，`select` 走从库 | 调用方无感 | 事务、函数、注释、大小写都会误判 |

项目选 **A 显式**。原因：我们的接口边界清晰，读接口和写接口本来就分开；自动解析 SQL 带来的隐蔽 bug 比省下的几行代码更贵。

```python
with db.write_conn() as conn:   # POST /profile
    ...

with db.read_conn() as conn:    # GET /profile
    ...
```

## 三、真实 bug：写后立刻读，读到了空对象

生成路径的代码原来是这样：

```python
path_id = store.create_path(...)      # 写主库
path = store.get_path(path_id)        # 默认读从库
return decorate_path(path or {})
```

接口返回了 `200`，但 `data` 是 `{}`。

原因：**主从复制有延迟**。主库刚写入，从库还没重放完，`SELECT` 在从库查不到这一行。

这类场景叫 **read-your-writes（读己之写）**。解决方式不是「把主从延迟调成 0」（做不到），而是明确告诉代码：这一次读必须走主库。

```python
path = store.get_path(path_id, use_master=True)
```

同理，以下场景都应该读主库：

- 刚创建完，立刻返回详情；
- 同一个请求里先写后读；
- 事务内的读写；
- 对一致性要求高的后台任务。

而「用户下一次打开页面」「列表浏览」这类场景，读从库完全够用。

> 判断依据不是「读还是写」，而是「这次读能不能接受旧数据」。

## 四、从库挂了怎么办？

`read_conn()` 在获取连接失败时降级主库：

```python
try:
    conn = read_pool.acquire()
except Exception as exc:
    logger.warning("从库不可用，读请求降级主库：%s", exc)
    with write_pool.connection() as fallback:
        yield fallback
    return
```

注意两个细节：

1. **只对「获取连接失败」降级**，不对「SQL 执行失败」降级。否则一个 SQL 语法错误会在主库再执行一遍，问题被掩盖。
2. **降级必须打日志**。否则从库挂了半年你都不知道，读写分离形同虚设。

`/api/health` 会分别探测主库和从库：

```json
{
  "database": {
    "master": { "ok": true, "port": 3306 },
    "replica": { "ok": true, "port": 3307 }
  }
}
```

从库不可用时，`replica.ok=false`，`services.replica_fallback=true`。

## 五、事务：一个事务必须在一个连接上

MySQL 的事务是连接级的。下面这种写法是错的：

```python
with write_conn() as conn:
    insert(conn)
with read_conn() as conn:
    select(conn)       # 不在同一个事务里
```

正确做法：事务内的所有读写都用同一个连接，并且这个连接来自主库。

```python
with write_conn() as conn:
    with conn.cursor() as cur:
        cur.execute("INSERT ...")
        cur.execute("SELECT ...")   # 同一个连接，读得到
```

连接池的 `connection()` 上下文管理器统一 commit / rollback：

```python
try:
    yield conn
    conn.commit()
except Exception:
    conn.rollback()
    raise
finally:
    pool.release(conn)
```

## 六、怎么验证真的分流了？

至少三种办法：

1. **看健康检查**：主从都有端口和状态。
2. **停掉从库**：读接口应该降级主库（我们的设计），写接口正常；日志出现 WARNING。
3. **在从库改一条数据**：如果 GET 返回从库版本，说明读确实走了从库；再等复制追上，又回到主库版本。

本项目实际验证：

- 教学接口 `GET /api/debug/db-route` 返回 `{"write_port":3306,"read_port":3307}`，直接证明分流；
- `health` 返回主从均 `ok`；
- 从库用空密码启动时，读请求自动降级，日志有 WARNING；
- 重新配置从库密码后，读写分离恢复正常；
- 路径接口从 `{}` 修复为完整 5 步路径，证明 `use_master=True` 生效。

> **调试方法论**：先看接口返回，再看日志，再看数据库状态，最后才改代码。不要一上来就怀疑框架。

## 七、连接池参数怎么定？

当前配置：

```env
DB_POOL_SIZE=8
DB_CONNECT_TIMEOUT=3
```

经验：

- 池大小不是越大越好。MySQL 的 `max_connections` 有限，池太大反而会增加上下文切换；
- 先按「并发请求数 × 每个请求占用连接时间」估算，再压测；
- 读池和写池要分开：读多写少时，读池可以更大；
- 一定要设连接超时和读超时，避免请求无限挂起。
