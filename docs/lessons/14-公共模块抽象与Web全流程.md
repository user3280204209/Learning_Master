## 一、公共模块抽象（分块一第 1 条）

### 拆分前 vs 拆分后

```
拆分前：backend/main.py 一个文件装下所有东西

拆分后：
backend/
├── main.py            # 入口：创建 app，注册路由（只有"接线"的职责）
├── models.py          # 数据模型 + 公共基础类
├── db.py              # 数据库连接
└── routers/
    └── profile.py     # 画像相关接口
```

### 抽象出的公共基础类

`models.py` 里的 `ApiResponse`——**统一响应格式**：

```python
class ApiResponse(BaseModel):
    code: int = 0          # 0=成功，非0=业务错误
    message: str = "ok"
    data: dict | None = None
```

所有接口都返回这个格式，前端就不需要"每个接口各猜一种返回形状"。这是真实项目里最常见的公共抽象。

### 拆分的判据（第 7 课讲过的，现在落地了）

> **按"变化的理由"拆**：接口定义、数据模型、数据库连接，三者变化的理由不同，所以是三个文件。

## 二、Web 访问全流程（分块一第 2 条）

结合你项目的**真实架构**（不是教科书上的空话），一次访问 `http://127.0.0.1:8088/profile/1` 发生了什么：

```
① 浏览器输入 URL
    ↓ DNS 解析（这里是 127.0.0.1，跳过）
② 浏览器 → Nginx 建立 TCP 连接（三次握手）
③ 浏览器发出 HTTP GET 请求
④ Nginx(8088) 收到 → 按 upstream 轮询，转发给 8001 或 8002（反向代理+负载均衡）
⑤ uvicorn 收到 → 调 FastAPI 应用
⑥ FastAPI 路由匹配 /profile/1 → 调 get_profile 函数
⑦ get_profile → pymysql 连 MySQL（读写分离：读走从库 3307）
⑧ MySQL 执行 select → 返回行
⑨ FastAPI 包成 ApiResponse → 返回
⑩ uvicorn → Nginx → 浏览器
⑪ 浏览器解析 JSON，渲染显示
```

### 三个关键认知

1. **"服务器"不是一台机器，是好几层**：Nginx（入口）→ uvicorn（应用服务器）→ FastAPI（应用）→ MySQL（数据）。每层各司其职。
2. **反向代理的意义**：浏览器只知道 Nginx（8088），不知道背后有 8001/8002 两台、更不知道有 MySQL。**隐藏后端结构**。
3. **读写分离的落点**：第 ⑦ 步——**读**操作连从库（3307），**写**操作连主库（3306）。数据层已经备好主从，应用层在 `db.py` 里分两个连接就能用。

> 面试常问："一个请求进来，中间发生了什么？"——现在你能用上面这张 11 步的链路，结合自己的项目完整讲出来，而不是背"DNS→TCP→HTTP"的套话。
