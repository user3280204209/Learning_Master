## 一、为什么大文件要分片上传

大文件（视频、动画）直接单次上传有三个问题：

1. **超时**：HTTP 请求久了会断，几百 MB 一次传不完
2. **不可恢复**：传到 90% 断了，从头再来
3. **不能并行**：单连接慢

**分片上传**（云厂商叫 **multipart upload**）解决它：切成小片，逐片传，断了只重传断的那片，最后按顺序拼回来。

```
文件 → [片0] [片1] [片2] ... [片N]
        ↓     ↓     ↓         ↓    （逐片 / 并行上传）
      后端存到 uploads/{file_id}/{序号}
        ↓
     全部到齐 → 按序号 0..N 顺序拼回完整文件
```

## 二、实现（backend/routers/upload.py）

两个接口：

| 接口 | 作用 |
|---|---|
| `POST /upload/chunk` | 收一片，存到 `uploads/{file_id}/{chunk_index}` |
| `POST /upload/complete` | 全部到齐后，按 0..N 顺序拼成最终文件 |

核心代码（重组）：

```python
with open(final_path, "wb") as out:
    for i in range(total_chunks):
        with open(os.path.join(chunk_dir, str(i)), "rb") as f:
            shutil.copyfileobj(f, out)   # 按序号顺序拼接
```

### 验证结果（真实）

3MB 随机数据 → 分 3 片上传 → 重组，`内容一致: True`，大小 3145728 字节。

## 三、小文件批量读写

小文件（头像、缩略图）的特点：数量多、单个小（几 KB）。一个个传太慢，用**批量接口**一次传多个：

```python
@router.post("/batch")
async def upload_batch(files: list[UploadFile] = File(...)):
    # 一次请求接收多个小文件，逐个落盘
```

验证：3 个小文件一次传完，返回 `count: 3`。

> **小文件方案的进阶思路**（面试可讲）：小文件太多会拖垮文件系统（inode 耗尽、寻址慢），生产上常把它们**打包成一个"合并文件"**（如每个用户一个 tar/对象），用索引记录"哪个文件在哪个偏移、多长"。这就是对象存储（OSS/MinIO）底层干的事。

## 四、云 OSS 和开源文件服务器

### 云 OSS（阿里 OSS / 腾讯 COS / AWS S3）

云厂商的对象存储服务。你要传大文件，调它的 **multipart upload** 接口——**原理就是你上面实现的分片上传**。区别只是：分片存在云端、由它帮你重组、给你一个可下载的 URL。

> 所以你现在写的 `upload.py`，就是 OSS 分片上传的**本地精简版**。理解了它，再看 OSS SDK 就不陌生了。

### 开源文件服务器（分块三第 2 条：下载开源文件服务器读代码）

两个主流开源选择：

| 工具 | 特点 |
|---|---|
| **MinIO** | Go 写的，S3 兼容对象存储，单文件可部署，最流行 |
| **FastDFS** | C 写的，国产轻量分布式文件系统 |

**读代码的顺序**（按这个顺序看，不要从头读）：

1. **接口定义**：`object-api-interface.go:279-295`
   看 `PutObject`、`NewMultipartUpload`、`PutObjectPart`、`CompleteMultipartUpload` 四个方法签名——这就是 S3 分片上传的三步（Initiate → UploadPart → Complete）。
2. **HTTP 路由**：`api-router.go:315-329`
   看 URL 是怎么映射到 `api.PutObjectPartHandler` 等 handler 的。
3. **handler 层**：`object-multipart-handlers.go`
   - `NewMultipartUploadHandler`（:64）→ 创建 uploadID
   - `PutObjectPartHandler`（:590）→ 接收一片
   - `CompleteMultipartUploadHandler`（:914）→ 合并
   这一层只做参数解析和鉴权，真正的逻辑在下一层。
4. **核心实现**：`erasure-multipart.go`
   - `newMultipartUpload`（:376）→ 建 uploadID 目录、写元数据
   - `PutObjectPart`（:575）→ 每片写临时文件 + 记录 part 信息
   - `CompleteMultipartUpload`（:1096）→ 按 part 列表合并、校验 ETag、写最终对象
5. **落盘细节**：`xl-storage.go`
   - `CreateFile`（:2092）→ 创建分片文件
   - `AppendFile`（:2324）→ 追加写
   - `RenamePart`（:2920）→ 临时分片改名为正式对象
   - `ReadFile`（:1868）→ 按 offset 读

> **和你的 `upload.py` 对照**：`/upload/chunk` ≈ `PutObjectPart`；`/upload/complete` ≈ `CompleteMultipartUpload`；`uploads/{file_id}/` ≈ uploadID 目录。区别是 MinIO 还会把每片切成 data/parity 分片做纠删码，并写 `xl.meta` 元数据——这是分布式对象存储多出来的部分，不是分片上传的本质。
