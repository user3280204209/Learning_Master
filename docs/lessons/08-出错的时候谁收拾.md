# 第 8 课：出错的时候，谁来收拾？

> **日期**：2026-10-19
> **前置**：第 6 课（对象）、第 7 课（数据库接进接口）
> **目标**：理解"异常会跳过收尾代码"这个隐患，学会 `try/finally` 和 `with`

## 一、一个你还没注意的漏洞

看你第 7 课写的 `create_profile`：

```python
def create_profile(req: ProfileRequest):
    conn = db.get_conn()        # ① 拿到连接
    cur = conn.cursor()         # ② 拿到游标
    cur.execute("insert ...")   # ③ 插入
    new_id = cur.lastrowid      # ④
    conn.commit()               # ⑤ 提交
    conn.close()                # ⑥ 关闭
    return {"id": new_id}
```

**看起来没问题。但把"出错"考虑进去，它就有洞了：**

```
③ 如果这里抛出异常 → ④⑤⑥ 全部被跳过
```

`conn.close()` **永远不会执行**。

### 而这恰恰是最需要关闭连接的时候

| 情况 | 会发生什么 |
|---|---|
| 一切正常 | 关闭 ✅ |
| 中间出错 | **不关闭** ❌ |

**这很反直觉**：**越是有问题的时候，越需要收尾**——但普通的顺序执行，恰恰是出错时就跳过了收尾。

> 这就是 `finally` 存在的理由。

### 连接不关会怎样

- 每个连接占一个**文件句柄**，还占内存
- 操作系统对单个进程的文件句柄数**有上限**
- 接口被调用几千次都出一次错 → 句柄耗尽 → 整个服务卡死

> **这类问题叫"资源泄漏"（resource leak）。**
> 它的特点是：**平时完全正常，压力一大就崩，而且崩的时候看不出原因。**
> 实习时这类 bug 排查起来非常痛苦，因为复现都难。

还有一个更隐蔽的：**事务没 `commit` 也没回滚**。连接一关，未提交的改动被丢弃——有时是应该的，有时不是。

## 二、先做个实验，看看"跳过"是真的

新建一个临时脚本（跑完就可以删），`backend/exp_exception.py`：

```python
import sqlite3

conn = sqlite3.connect(":memory:")      # 内存库，不落盘，随便炸
cur = conn.cursor()
cur.execute("create table t(name text not null)")
conn.commit()


def try_insert(bad_value):
    print("开始执行")
    cur.execute("insert into t(name) values (?)", (bad_value,))
    print("插入成功")                   # ← 这行会被执行到吗？
    conn.commit()                       # ← 这行呢？


try:
    try_insert(None)                    # name 是 not null，传 None 必炸
except Exception as e:
    print("捕获到异常：", type(e).__name__, e)

print("--- 函数外面，这里一定会执行 ---")
conn.close()
```

跑：

```bash
cd backend
python exp_exception.py
```

**把输出贴给我。** 重点看：`插入成功` 和 `conn.commit()` 那两行，**有没有出现**。

> ⚠️ 你的 `db.py` 里 `create table` 要求 `name text not null`。这正是能让它炸的地方——**用 `None` 去违反一个约束，是最省事的"人为制造异常"手法**，以后调试常用。

## 三、`try / finally`：无论在不在中间炸，都要执行

```python
conn = db.get_conn()
cur = conn.cursor()
try:
    cur.execute("insert ...", (...))
    new_id = cur.lastrowid
    conn.commit()
except Exception:
    raise                       # 出错了就按原样往外抛
finally:
    conn.close()                # 不管成功、失败、还是 return，都执行
```

**`finally` 的三个保证**：

| 情况 | `finally` 执行吗 |
|---|---|
| 正常走完 | ✅ |
| 中间抛异常 | ✅ |
| 中间写了 `return` | ✅ |

> **`finally` 是"无论如何都要做的事"的专用位置。**

上面的 `except Exception: raise` 其实**可以省略**——这么写是为了让你看清结构。真正有用的写法是：

```python
try:
    ...
finally:
    conn.close()
```

**Python 允许 `try` 后面只跟 `finally`，不跟 `except`。** 意思是"我不处理异常，我只要保证收尾"。异常照样往外抛。

## 四、`with`：`try/finally` 的马甲

`try/finally` 谁写都烦。所以 Python 提供了 `with`：

```python
with 某个东西 as 变量名:
    干活
# 出了这个块，收尾自动完成
```

**`with` 块结束（无论正常结束还是抛异常），都会自动调用"收尾"逻辑。**

你现在不用手写 `close()` 了。但**"什么才算收尾"，是那个东西自己决定的**——这就是下一节要知道的坑。

### 4.1 一个非常大、非常常见的坑

你可能会想：`sqlite3.connect()` 返回连接，那我直接 `with` 它不就完事了？

```python
with sqlite3.connect("student.db") as conn:      # 看起来很美
    conn.execute("insert ...")
# 连接关了吗？—— 没有！
```

**`with` 一个 Connection 对象，只管"事务"（提交 / 回滚），不管"关闭"。**

也就是说：

- 正常结束 → `commit()`
- 抛异常 → `rollback()`
- **`close()` 一次都没调用**

**验证方法**（自己跑，别信我）：

```python
import sqlite3

with sqlite3.connect("test_conn.db") as conn:
    conn.execute("create table t(a text)")
    conn.commit()

# 出了 with，试试这个连接还能不能用
try:
    print(conn.execute("select 1").fetchall())
    print("→ 连接还活着：with 并没有关闭它")
except Exception as e:
    print("→ 连接已关闭：", e)

conn.close()
```

> **这跟第 5 课的 `commit` 坑是同一类教训**：
> **看起来像"应该会做的事"，不等于它真的会做。**
> **一个 `with` 说它"管理了连接"，你可能就信了。**

跑完把 `test_conn.db` 删掉。

## 五、自己写一个上下文管理器（**这一节和第 6 课是连着的**）

`with` 到底是怎么知道该调什么收尾逻辑的？

**答案：它找对象上的两个方法。**

| 方法 | 什么时候被调用 | 干什么 |
|---|---|---|
| `__enter__` | 进入 `with` 块时 | 准备资源，**返回值给 `as` 后面的变量** |
| `__exit__` | 离开 `with` 块时（**异常也走这里**） | 收尾：提交 / 回滚 / 关闭 |

**只要一个对象有这两个方法，它就能被 `with` 使用。** 这种对象叫**上下文管理器**。

> 名字里那两个下划线（dunder，double underscore）是 Python 的"协议"——**不是给你直接调用的，是给语言在特定时机调用的**。
> 你在第 6 课已经见过 `class ProfileRequest(BaseModel)` 了，Pydantic 也是靠类似机制工作的。

### 5.1 在 `db.py` 里加一个

```python
class DBConnection:
    """用 with 管理的数据库连接。"""

    def __init__(self, path):
        self.path = path       # str，数据库文件路径
        self.conn = None       # sqlite3.Connection，进入时才创建

    def __enter__(self):
        self.conn = sqlite3.connect(self.path)
        return self.conn       # ← with ... as conn 拿到的就是它

    def __exit__(self, exc_type, exc_value, traceback):
        # exc_type 是 None → 没出错；否则就是异常的类型
        if exc_type is None:
            self.conn.commit()
        else:
            self.conn.rollback()
        self.conn.close()
        # 返回 None（假值）→ 异常继续往外抛，不被吞掉
```

**逐行对照第 6 课的三种东西**：

| 代码 | 属于哪一类 |
|---|---|
| `class DBConnection:` | **类**（图纸） |
| `self.conn` | **属性**（数据） |
| `__enter__` / `__exit__` | **方法**（动作） |
| `DBConnection("student.db")` | **实例化**，得到一个**对象** |

### 5.2 `__exit__` 的三个参数

```python
def __exit__(self, exc_type, exc_value, traceback):
```

| 参数 | 含义 | 没出错时是 |
|---|---|---|
| `exc_type` | 异常的类型（如 `OperationalError`） | `None` |
| `exc_value` | 异常对象本身 | `None` |
| `traceback` | 调用栈信息 | `None` |

**所以 `if exc_type is None` 就是判断"这次有没有出事"。**

### 5.3 返回值很关键

- **返回 `None`（或 `False`）** → 异常**照常往外抛**
- **返回 `True`** → 异常**被吞掉**，后面的代码以为一切正常

**默认什么都别返回（= 返回 `None`）。** 吞异常通常是很危险的做法——还记得上一课我们为什么否掉"try/except 吞掉 `duplicate column`"吗？

## 六、动手改造

### 6.1 `db.py`

在 `DBConnection` 下面加一个函数，让调用方少写点：

```python
def get_db():
    return DBConnection(DB_PATH)
```

然后 `main.py` 里：

```python
from fastapi import HTTPException, FastAPI
from pydantic import BaseModel

import db

db.init_db()
app = FastAPI()
```

**注意原来的 `db.get_conn()` 别急着删**——`init_db()` 还在用它。两种写法并存没问题。

### 6.2 改造两个接口

```python
@app.post("/profile")
def create_profile(req: ProfileRequest):
    with db.get_db() as conn:
        cur = conn.cursor()
        cur.execute(
            "insert into students(name, major, age, goal) values (?, ?, ?, ?)",
            (req.name, req.major, req.age, req.goal),
        )
        new_id = cur.lastrowid
    return {"id": new_id}
```

**注意：`commit()` 和 `close()` 都不见了——它们现在归 `__exit__` 管。**

读接口一样：

```python
@app.get("/profile/{student_id}")
def get_profile(student_id: int):
    with db.get_db() as conn:
        cur = conn.cursor()
        cur.execute(
            "select id, name, major, age, goal from students where id = ?",
            (student_id,),
        )
        row = cur.fetchone()

    if row is None:
        raise HTTPException(status_code=404, detail="不存在这个学生")
    ...
```

> **`raise HTTPException` 为什么要放到 `with` 外面？**
> 放里面也**能正常工作**（`__exit__` 会回滚，然后异常继续抛）。
> 但既然查询已经结束、连接也用完了，早点退出更清楚。**这是可读性的选择，不是正确性的要求**——知道这个区别，比记住写法重要。

### 6.3 关于 `init_db()`

`init_db()` 还在手动 `connect/commit/close`。可以一起改成：

```python
def init_db():
    with get_db() as conn:
        cur = conn.cursor()
        cur.execute("""create table if not exists students(...)""")
```

**改完再跑一遍第 7 课的三条验证**：

1. 写入 → 拿 id
2. 读出 → 对得上
3. **重启后再读 → 数据还在**

第 3 条尤其重要：`__exit__` 里要是漏了 `commit`，数据就写不进去，**而且不会报错**。

## 七、这套东西以后还会在哪出现

你现在学的不是"SQLite 专用技巧"。**"用完必须还回去"的资源到处都是**：

| 资源 | 泄漏的后果 |
|---|---|
| 数据库连接 | 句柄耗尽，服务卡死 |
| 打开的文件 | 文件被锁住，别的程序写不了 |
| 网络连接 | 连接池耗尽，请求全部超时 |
| 线程 / 进程 | 内存和 CPU 越用越多 |
| **LLM API 调用** | 计费停在半路，或者重试逻辑打乱 |

**你项目里很快就要调大模型 API——网络请求是最容易出事的资源。** 现在把这个习惯建立起来，比那时候补要省事得多。

> 还有一个后面会讲的东西：**FastAPI 的 `Depends` + `yield`**，能自动管理"每个请求一个连接"，而且一个请求里多个函数共用同一个连接。等拆分项目结构的时候再说。

## 十、备忘

- **异常会跳过后面所有代码**——包括本该执行的收尾
- `try/finally`：`finally` 一定执行（正常 / 异常 / return）
- `with` = `try/finally` 的马甲，靠对象的 `__enter__` / `__exit__` 工作
- ⚠️ **`with sqlite3.connect(...)` 只管提交/回滚，不关连接**
- `__exit__` **返回 `True` 会吞掉异常**——默认别返回
- 资源泄漏：平时没事，压力一大就崩
- 启动命令还是 `uvicorn main:app --reload --port 8001`（在 `backend/` 下）
