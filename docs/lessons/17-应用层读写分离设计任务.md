## 二、这次不写代码，先回答 5 个问题

按顺序把答案写在本节下面（可以先写关键词，不用成文）。

### 1. 连接怎么管？

现在每次 `with get_conn() as conn:` 新建一个 pymysql 连接。读库和写库各要一个连接来源。

- 用「两个函数」`get_write_conn()` / `get_read_conn()` 够不够？
- 要不要引入连接池？为什么？（提示：FastAPI 是并发处理请求的）
- 连接池放在哪里？模块级全局变量、应用启动时创建，还是每个请求创建？

### 2. 读 / 写怎么选？

两种路线：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 显式 | 写接口调用 `get_write_conn()`，读接口调用 `get_read_conn()` | 简单、可控 | 每个接口都要记得选对 |
| B 自动 | 解析 SQL，`select` 走从库，其余走主库 | 调用方无感 | 事务、函数调用、大小写、注释都会误判 |

你选哪条？为什么？**我不需要你选"更高级"的，需要你说清楚代价。**

### 3. 事务怎么办？

场景：一个请求里先 `insert`，紧接着 `select` 刚插入的数据。

- 如果 select 走从库，可能读不到（主从延迟）。
- 那这种请求应该读主库还是从库？判断依据是什么？
- 如果用连接池，一个事务的读写必须在**同一个连接**上，这一点怎么保证？

### 4. 接口怎么改？

以现有的 `/profile` 为例：

- `POST /profile` 写 `student` / `profile_dimension` → 应走哪个库？
- `GET /profile/{student_id}` → 应走哪个库？
- 如果 GET 里要做"写后读"（比如刚创建完立刻查），怎么办？

### 5. 怎么验证真的分流了？

想一个**能证明读请求确实到了 3307** 的办法，至少写出一种：

- 提示 1：从库 `read_only=1`，如果读接口误走从库做写，会报错。
- 提示 2：可以临时在从库改一条数据，看 GET 返回的是主库版本还是从库版本。
- 提示 3：看 MySQL 的 `SHOW STATUS LIKE 'Questions'` / 慢日志。
- 提示 4：故意停掉从库，读接口应该报错，写接口应该正常。
