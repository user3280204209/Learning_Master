## 一、先纠正一个最常见的误解

> **很多人以为 Git = 把代码传到 GitHub。不是。**

Git 首先是一个**本地的时间机器**——记录代码的每一次演变，让你随时回到任何历史版本。

GitHub 只是额外加了两样东西：**云端备份** + **多人协作**。所以先学本地，远程是加一条命令的事。

---

## 二、核心心智模型：三个区域

理解 Git 的**唯一关键**：

```
工作区                暂存区                  版本库
(你正在改的文件)  →   (挑出来准备存档)   →   (真正存进历史)
                 git add              git commit
```

| 区域 | 是什么 |
|---|---|
| **工作区** | 你现在打开、正在编辑的那些文件 |
| **暂存区** | 你说"这些改动我打算存下来" |
| **版本库** | 真正变成一个历史节点 |

**为什么要多一个"暂存区"？** 因为一次提交应该是**一个完整的、有意义的改动**，而不是"我把今天所有乱七八糟的编辑都存了"。

> 这是 Git 和 `Ctrl+S` 备份的**本质区别**。

## 三、日常工作流

```bash
# ① 配置身份（一次就够）
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"

# ② 初始化仓库
git init

# ③ 看状态（最常用的命令）
git status

# ④ 挑选 → 存档
git add main.py .gitignore
git commit -m "feat: 跑通最小 FastAPI 服务"

# ⑤ 看历史
git log --oneline
```

> **`git status` 是 Git 里最常用的命令。不确定的时候先敲它。**
> 这跟"遇到报错先读报错"是同一个道理。

## 四、`.gitignore`：什么不该提交

```
.venv/
__pycache__/
*.pyc
.vscode/
```

**判断标准**：

> **能靠一条命令重新生成的，就不该提交。**

`.venv` 能（靠 `requirements.txt` 重建），`__pycache__` 能（自动生成的字节码缓存），但你的 `main.py` 不能。

**为什么 `.venv` 特别不能提交**：里面是几十上百 MB 的第三方包，那是**你电脑上的运行环境**，不是**你的代码**。

## 五、提交信息规范（Conventional Commits）

| 前缀 | 含义 |
|---|---|
| `feat:` | 新功能 |
| `fix:` | 修 bug |
| `docs:` | 只改文档 |
| `chore:` | 杂项（配置、依赖等） |
| `refactor:` | 重构，不改功能 |

**格式**：`类型: 描述` —— **冒号后面有一个空格，冒号前面没有空格**。

（踩过的坑：写过 `docs :添加lessons文件`，冒号前多了空格。）

> **实习时团队的提交记录会被 review**，写"111"、"改了下"是会被说的。

## 六、踩到的坑

### 坑 1：`.gitignore` 完全没生效

**现象**：`.venv` 没被提交，看起来一切正常。但用 `git check-ignore -v` 一测，**一条规则都没匹配上**。

**原因**：每行前面多了**两个空格**：

```
  .vscode/        ← 行首有空格
```

Git **不会忽略行首空格**，空格会成为模式的一部分。所以 `  .vscode/` 的意思是"忽略一个**名字里带两个空格**的目录"——永远匹配不到。

**对照实验结论**：

| 写法 | 结果 |
|---|---|
| `  .vscode/`（行首有空格） | ❌ 失效 |
| `.vscode/`（顶格） | ✅ 生效 |
| `.vscode/` + CRLF 换行 | ✅ 生效（换行符不是问题） |

**那 `.venv` 为什么没被提交？** **运气**——Python 创建 venv 时，自己在里面放了一个 `.gitignore`，内容就一个 `*`。所以 `.venv` 是被它自己忽略的，跟我们的规则毫无关系。

> **今天最值钱的教训**：
> **"看起来对了"和"真的对了"是两件事。**
>
> **改完要验证**，不要停在"应该好了"：
> ```bash
> git check-ignore -v .vscode/ __pycache__/
> ```
> **有输出 = 生效了。**

### 坑 2：cwd 又出现了

```bash
git add main.py            # ❌ 报错：在 Learning/ 下，这里没有 main.py
git add backend/main.py    # ✅ 正确的相对路径
```

**和第 1 课 uvicorn 那个坑是同一个知识点**：**相对路径是相对于"当前工作目录"解析的。**

> **同一个概念，两次遇到——说明它值得记牢。**

## 七、两条实用习惯

### 7.1 先看再加

```bash
git status      # 先看
git add ...     # 再加
```

很多人图省事敲 `git add .`（加当前目录所有改动）。**能用，但要慎用**——它会把所有没被忽略的东西一股脑加进去。

### 7.2 Git 很抗折腾

**你不 commit，改错了随时能退回来**，基本没有什么操作是不可逆的。所以放开手试。

## 九、备忘

- `git status` / `git add <文件>` / `git commit -m "类型: 描述"` / `git log --oneline`
- `git diff` —— 看改了**什么**（绿色 `+` 新增，红色 `-` 删除）
- `git checkout .` —— 丢弃所有未提交的改动，回到上次提交的状态
- `git check-ignore -v <路径>` —— 验证忽略规则是否生效
- **提交信息格式**：`feat:` / `fix:` / `docs:` / `chore:` + 空格 + 描述
